# ADR-0001: Разделение Event и Session

**Статус:** Принято  
**Дата:** 2026-09-09  
**Авторы:** команда Afisha

---

## Контекст

Система афиши работает с двумя концептуально разными вещами:

- **Произведение** — «Гамлет», «Щелкунчик», концерт группы X. У него есть описание, афиша, жанр, возрастное ограничение. Эти данные не меняются от показа к показу.
- **Показ** — конкретное исполнение произведения: площадка «Большой театр», 15 ноября в 19:00, цена от 2 000 ₽, 300 мест.

## Проблема

Если хранить всё в одной таблице (`events`), каждый показ будет содержать полную копию описания, афиши и метаданных произведения. Для «Гамлета» с 20 показами за сезон это означает:

- 20 копий одного и того же описания и URL афиши — избыточность данных.
- При редактировании описания нужно обновить все 20 строк — риск рассинхронизации.
- Запрос «покажи карточку события» возвращает дублирующиеся поля.
- Полнотекстовый индекс строится по одному и тому же тексту 20 раз.

## Решение

Разделить сущности на две таблицы:

### `events` — произведение

Хранит всё, что описывает само произведение и не зависит от конкретного показа: `title`, `description`, `category_id`, `age_rating`, `poster_url`.

### `sessions` — показ

Хранит всё, что специфично для конкретного исполнения: `event_id` (FK), `venue_id`, `city_id`, `starts_at`, `price`, `total_seats`, `seats_left`, `status`.

```
Event 1 ──< Session 1  (Большой театр, 15.11, 19:00)
            Session 2  (Большой театр, 16.11, 14:00)
            Session 3  (Малый театр,  20.11, 18:00)
```

## Последствия

### Положительные

- Описание и афиша хранятся ровно в одном месте — редактирование затрагивает одну строку (US-19).
- GIN-индекс по полнотекстовому поиску строится один раз на `events`, а не для каждого показа (US-02).
- Каталог строится JOIN'ом `sessions` → `events`, фильтруя по `sessions.city_id` и `sessions.starts_at` через составной индекс — единственная точка для оптимизации (US-01, US-03).
- Страница события (US-04, US-05) требует ровно двух запросов: один за `events`, один за `sessions WHERE event_id = ?`.

### Отрицательные / компромиссы

- `city` денормализован в `sessions` (дублирует `venues.city`), чтобы избежать JOIN при фильтрации каталога. При изменении города площадки нужно обновить и `sessions`. Это осознанный компромисс производительности над нормализацией.
- Запросы с агрегацией «минимальная цена события» требуют GROUP BY по session-уровню.

## Отклонённые альтернативы

### Одна таблица `events` с nullable полями

Отклонено: приводит к дублированию описания (см. «Проблема»). Попытка нормализовать через дополнительную таблицу `event_metadata` воспроизводит то же разделение, но с менее ясной семантикой.

### Наследование таблиц (PostgreSQL table inheritance)

Отклонено: добавляет сложность ORM-маппинга без практической выгоды для данного объёма.

## Связанные решения

- Индекс `idx_sessions_city_starts_at` — прямое следствие денормализации `city` в `sessions`.
- Схема таблиц описана в [docs/db-schema.md](../db-schema.md).
