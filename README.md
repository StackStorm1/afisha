# Быстрый старт

## Запуск через Docker

```bash
cp .env.example .env
docker compose up --build
```

Проверить, что backend поднялся:

```bash
curl http://localhost:8000/health
```

Должно вернуть `{"status":"ok"}`.

Фронтенд поднимается той же командой и открывается на
<http://localhost:8080>. В образе лежит только собранная статика за nginx —
для разработки с автоперезагрузкой запускайте `npm run dev`, он занимает
отдельный порт 5173 и стеку не мешает. См. `frontend/README.md`.

## Разработка backend без Docker

Нужен [uv](https://docs.astral.sh/uv/) — им поставлены все зависимости backend.

Postgres всё равно нужен в контейнере:

```bash
docker compose up -d db
```

Установка зависимостей и запуск сервера с автоперезагрузкой:

```bash
cd backend
uv sync
uv run --env-file ../.env uvicorn app.main:app --reload
```

`--env-file` обязателен. Приложение читает только переменные окружения и не
открывает `.env` само: в контейнере окружение наполняет docker-compose, на
хост-машине — эта команда. Путь загрузки настроек один и тот же везде, поэтому
конфигурация в Docker и локально не может незаметно разойтись.

Чтобы не повторять флаг, его можно задать один раз на сессию:

```bash
export UV_ENV_FILE=../.env
```

## Миграции и тестовые данные

Выполнять из `backend/`. Схема накатывается Alembic:

```bash
uv run --env-file ../.env alembic upgrade head
```

Миграции создают таблицы, индексы и триггеры, а справочники `cities` и
`categories` наполняет отдельная миграция данных — повторный накат ничего не
дублирует.

Площадки, места, события, сеансы, заказы и брони создаёт генератор:

```bash
uv run --env-file ../.env python -m app.cli.seed --truncate
```

По умолчанию получается 8 площадок, 420 событий, около 2100 сеансов и 4000
заказов. Объёмы меняются флагами `--venues`, `--events`,
`--sessions-per-event`, `--days`, `--orders`, `--buyers`, значения по умолчанию
покажет `--help`.

`--truncate` очищает только генерируемые таблицы (`bookings`, `orders`,
`sessions`, `seats`, `events`, `venues`) и покупателей генератора; справочники,
историю миграций и живые учётные записи не трогает. Вне `ENVIRONMENT=local`
флаг запрещён.

Для воспроизводимого набора данных задайте зерно:

```bash
uv run --env-file ../.env python -m app.cli.seed --truncate --seed 42
```

Одно и то же зерно даёт одни и те же идентификаторы, названия и расписание.
Это нужно, чтобы баг, найденный на сгенерированных данных, воспроизводился у
всей команды, а не только у того, кто его поймал.

### Учётные записи

Генератор создаёт семь технических покупателей `buyer-NN@seed.local`. Они
нужны только затем, чтобы у заказов и броней был владелец: пароль им выдаётся
случайный, печатается в конце прогона и входить под ними не предполагается.

Свой личный кабинет заводите сами через регистрацию в приложении: учётные
записи с доменом, отличным от `seed.local`, переживают `--truncate`.

По умолчанию все заказы принадлежат покупателям генератора, и список заказов у
своей учётной записи будет пустым. Чтобы часть заказов досталась
зарегистрированным пользователям:

```bash
uv run --env-file ../.env python -m app.cli.seed --truncate --orders-for-existing
```

## Тесты и линтер

Выполнять из `backend/`:

```bash
uv run --env-file ../.env pytest
uv run ruff check .
uv run ruff format --check .
```

Тестам нужен поднятый Postgres (`docker compose up -d db`) — проверка `/health`
ходит в базу. Линтеру и форматтеру окружение не нужно.
